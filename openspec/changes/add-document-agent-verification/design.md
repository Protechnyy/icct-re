## Context

动机见 proposal.md。这里只列影响方案的现状和约束。

- **抽取是并发的、按 batch 隔离的**。`DocumentPipeline._extract_relations` 用线程池并发处理 batch（默认 20 路），每个 batch 调一次 `extract_document(batch["text"])`，全部完成后 `_dedupe_relations` 做规则去重，得到 `final_relations`。
- **Worker 一次只处理一篇文档**（`worker.py` 是单线程循环），所以"文档级阶段串行执行"不会和别的文档抢资源。
- **索引的原料已经有了**。`relation_sections` 带小节编号、标题、原文、段落、页码和 block 编号；每条关系已经带 `source_sections`、`source_pages`、`source_paragraphs`。
- **模型调用层只支持单条 prompt**。`skill4re/backends.py` 用 `requests` 发单条 user 消息，不支持 `tools` 和多轮消息。后端环境里没有 `openai` 包。
- **任务状态是一整个 JSON**。`RedisTaskStore.update_task` 是读出、合并、整体写回，前端轮询状态接口。
- **已保存的结果足以离线重放**。`result.json` 里有 `document_text`、`relation_sections`、`final_relations`。
- **没有标注数据和打分代码**。`skill4re/examples/` 里只有跑抽取的脚本。
- **模型是 27B 的 Qwen，走百炼**。中等规模模型，工具多、任务大、循环长时容易出错。

## Goals / Non-Goals

**Goals:**

- agent 阶段是一个可整段摘除的独立模块，摘除后流水线与现在逐字节一致。
- 每一次模型调用对 27B 的模型都是"小而明确"的：工具少、输入短、目标单一。
- 对百炼的调用压力可预测、可封顶。
- agent 的每一处改动都能追溯到原文，并且可以被人工逐条检验。

**Non-Goals:**

- 不改抽取阶段、路由、共指消解和现有的"低置信度反思"。它们继续在 batch 内运行。
- 不引入向量检索和嵌入模型。
- 不做 agent 阶段内的并行任务调度（见决策 5）。
- 不把抽取链路迁到 LangGraph。

## Decisions

### 1. agent 放在规则去重之后，作为独立阶段

```
 batch 并发抽取 --> 规则去重 --> [核查阶段] --> 最终结果
                                  |
                                  +-- 关闭或失败: 直接用规则去重的结果
```

在 `process_task` 里、`_extract_relations` 返回之后插入。核查阶段的输入是规则去重后的关系列表、`relation_sections` 和 `document_text`，输出是新的关系列表加一个 `agent_result`。规则去重的结果另存为 `pre_agent_relations`，供回退和离线重放使用。

备选：放进每个 batch 内部，替换"低置信度反思"。否决原因：batch 内的原文本来就整段在 prompt 里，检索工具没有真实用处；跨小节的指代也只有在文档层面才解得开。

### 2. 用 LangGraph 编排，三个节点加一份状态

```
 +--------+     +----------------+     +----------+
 | 规划    | --> | 执行一个任务    | --> | 汇总      |
 +--------+     +----------------+     +----------+
                    ^         |
                    +---------+  还有任务且预算未耗尽
```

- **规划节点**：一次模型调用，结构化输出任务清单。
- **执行节点**：对当前任务跑工具循环，用框架预制的工具循环组件；循环步数用框架的递归上限封顶。
- **汇总节点**：纯代码，生成核查摘要。
- **状态**：任务清单、当前下标、工作中的关系图、记忆（别名表、已确认结论）、轨迹、预算计数。

用框架的按步流式输出把每一步转成进展事件。

备选：手写循环。它没有新依赖、调试更直接，但规划、状态传递、流式事件都要自己写。用户明确选择用框架来省掉这部分。备选：Qwen-Agent，结构偏对话助手，规划和记忆仍需自己搭。

模型通过框架的 OpenAI 兼容适配器连百炼。agent 用独立的一组配置（地址、密钥、模型名），不复用抽取链路的 `VLLM_*`，这样抽取和核查可以用不同的模型服务。

### 3. 规则分诊只提供线索，任务清单由模型定

分诊是纯代码，不调模型，产出"疑点"列表：

| 疑点 | 判定方式 | 对应任务类型 |
| --- | --- | --- |
| 证据在全文中定位不到 | 复用 `normalization/evidence.py` 的 `text_contains` | 核查证据 |
| 头实体或尾实体不在证据句中 | 字符串包含 | 核查证据 |
| 规则置信度低于 0.5 | 复用 `relation_confidence` | 核查证据 |
| 实体名像指代（以"该、其、本、上述"开头） | 前缀匹配 | 归一实体 |
| 不同小节出现写法相近的实体名 | 复用 `fuzzy_entity_match` | 归一实体 |
| 小节字数多但关系数明显偏少 | 关系数与字数之比低于文档中位数的三分之一 | 检查小节漏抽 |

规划提示词给模型看：实体列表（名称、出现次数）、各小节的标题和关系数、疑点列表。模型输出有序任务清单，每项含类型、目标（关系编号、实体名或小节编号）、理由。代码校验目标是否存在，丢弃无效项，截断到上限。

规划失败时退回为"把疑点直接当任务"，按上表映射，按疑点严重程度排序。

备选：完全由规则决定任务。否决原因：那样模型只在循环内部有自主性，体现不出规划。备选：不给疑点，让模型看全部关系自己找。否决原因：一篇文档可能有几百条关系，27B 的模型容易漏项，输入也过长。

### 4. 每类任务只给相关的工具，不超过 5 个

| 任务类型 | 可用工具 |
| --- | --- |
| 核查证据 | 检索原文、读取小节、定位证据、更正关系、删除关系 |
| 归一实体 | 查询实体、检索原文、读取小节、合并实体 |
| 检查小节漏抽 | 读取小节、查询实体、定位证据、补充关系 |

工具参数尽量只有一两个字符串。任务结束不设专门的工具：模型不再调用工具并给出一段结论，就算结束。

检索用字符二元组做 BM25，索引单位是段落，在核查阶段开始时从 `relation_sections` 现建，不落盘。中文不需要分词器，也不加依赖。

所有修改动作作用在关系图的工作副本上，并在代码层强制校验（证据必须能在原文中定位、规范名称必须在原文中出现、删除必须带理由、单任务新增不超过 5 条）。校验不通过时把原因作为工具结果返回，让模型自己纠正。约束放在代码里而不是提示词里，是因为不能指望 27B 的模型每次都遵守。

### 5. 任务串行执行，预算封顶

用户明确要求并发保守。默认值：

| 配置项 | 默认值 | 说明 |
| --- | --- | --- |
| `AGENT_ENABLED` | `false` | 评估通过前不默认开启 |
| `AGENT_CONCURRENCY` | `1` | 同时进行的核查模型调用数 |
| `AGENT_MAX_TASKS` | `20` | 单篇文档的任务数上限 |
| `AGENT_MAX_STEPS` | `6` | 单个任务的循环步数上限 |
| `AGENT_MAX_LLM_CALLS` | `80` | 单篇文档的模型调用总数上限 |
| `AGENT_TIMEOUT_SECONDS` | `600` | 单篇文档核查阶段的总时长上限 |
| `AGENT_MAX_ADDED_PER_TASK` | `5` | 单个任务可补充的关系数 |

任务串行有两个理由：一是记忆要求顺序（后面的任务要用前面确认的别名）；二是串行时对百炼的压力就是"一个连接、一个接一个地调"，最容易预测。`AGENT_CONCURRENCY` 留作配置项，但第一版只实现串行，大于 1 的值按 1 处理并打日志。

遇到限流（HTTP 429）按退避重试，重试计入调用预算。

抽取阶段的 `RELATION_BATCH_CONCURRENCY` 默认 20，是针对现有网关调的。如果抽取也切到百炼，建议降到 4 左右；这只是配置值的调整，在 README 里写明，本次不改默认值。

### 6. 记忆是一份精简的文本，随任务注入

记忆有两部分：别名表（规范名称到别名列表）和已确认结论（每个任务结束时的一句话结论）。执行每个任务前，只取与该任务目标相关的条目（涉及同一实体或同一小节）拼进提示词，总长度封顶约 800 字。

合并实体的工具在生效时同步写别名表，所以记忆的更新不依赖模型"记得去记"。

记忆只存在于图的状态里，文档处理完即丢弃。

### 7. 轨迹和进展

轨迹是一个事件列表，每个事件：

```
{ "seq": 12, "task_id": "t3", "kind": "tool",
  "tool": "locate_evidence", "args": {...},
  "result": "...(最多 500 字)", "truncated": false,
  "elapsed_seconds": 0.02 }
```

`kind` 取值：`plan`、`task_start`、`tool`、`conclusion`、`task_end`、`error`。模型的中间思考文本不保存，只保存工具调用和最终结论。

结果里新增顶层字段 `agent_result`：

```
agent_result:
  status          完成 / 部分完成 / 失败 / 跳过 / 未开启
  summary         任务数、各类改动数、调用次数、令牌数、耗时
  tasks           任务清单及各自状态和结论
  trace           事件列表
  removed_relations   被删除的关系及理由
  entity_aliases      别名表
pre_agent_relations   规则去重后的关系列表
```

每条关系新增 `relation_id`（稳定编号，在规则去重之后分配）和 `verification`（状态、涉及的任务编号）。原有字段不动。

进展：新增任务阶段 `agent_verification`，进度区间 70 到 84（抽取是 55，合并是 85）。任务状态里新增 `agent_progress`（任务总数、已完成数、当前任务描述、最近 20 条事件）。每个任务开始和结束、每次工具调用后写一次状态。因为是串行执行，`update_task` 的"读出再整体写回"不会有并发写的问题。

前端在 `ResultViewer` 里加一个核查摘要区和每条关系的核查详情抽屉，处理中的任务在日志区显示 `agent_progress`。

### 8. 失败回退分三层

1. **工具层**：参数不合法、校验不通过，把错误返回给模型，循环继续。
2. **任务层**：单个任务抛异常或达到步数上限，标记该任务失败或未完成，继续下一个。已生效的修改保留，因为每个修改动作在生效时都已通过原文校验。
3. **阶段层**：规划之外的整体性失败（模型服务不可用、预算耗尽、超时），停止执行。若一个任务都没完成，最终结果取 `pre_agent_relations`；否则取当前工作副本，状态标为部分完成。

整个核查阶段包在一个异常边界里，任何未预料的异常都落到"取 `pre_agent_relations`、状态标为失败"，不会让文档任务失败。

### 9. 评估：离线重放加人工判定改动

没有标注数据，从零标注整篇文档的全部关系成本很高。所以评估以"检验 agent 的改动"为主，以"与标注对比"为辅。

- **重放脚本**：读已保存的 `result.json`，取 `pre_agent_relations`（旧结果里没有该字段时取 `final_relations`），只跑核查阶段，输出到单独的目录。不需要 OCR、Redis 和前端。
- **自动指标**（不需要人工）：核查前后的关系总数、证据可定位占比、不同实体名数量、各类改动数量、调用次数、令牌数、耗时。
- **改动清单**（需要人工，但工作量小）：导出 CSV，每处改动一行，带改动前后内容、原文依据、页码和一列空白的判定。人只需要判断 agent 改过的那几十处对不对，不需要标整篇文档。填完后脚本算改动正确率，并按类型细分。
- **与标注对比**（可选）：如果有人为某篇文档标了关系，脚本算核查前后的精确率、召回率和 F1。匹配规则：头实体、关系、尾实体三者规范化后相等。

默认开启的门槛，在至少 5 篇不同类型的文档上：

- 改动正确率不低于 80%，其中删除类不低于 90%（错删的代价最高）；
- 证据可定位占比不下降；
- 单篇文档核查阶段耗时的中位数不超过 5 分钟。

达不到门槛时保持默认关闭，根据改动清单里的错误类型调整提示词和分诊规则后再测。

### 10. 依赖与部署

新增依赖：LangGraph 和它的 OpenAI 兼容适配器，加到 `backend/requirements.txt`。实施的第一步是在后端环境里试装并跑通现有测试。

如果与 `paddleocr==3.7.0`、`paddlepaddle==3.3.1` 冲突，退路是把 OCR 切到 HTTP 模式：`paddle_ocr.py` 已有这条路径，`paddleocr` 只在 `python_api` 模式下才被导入，切换后后端环境可以去掉 paddle 相关依赖。这条路径自 5 月后默认值改回了 `python_api`，在当前版本上是否仍然可用需要验证。

## Risks / Trade-offs

- **27B 的模型在工具调用上不稳定（调错工具、参数格式错、重复调用）** → 每类任务最多 5 个工具、参数极简、步数封顶；错误作为工具结果返回让它自纠；重放脚本可以在不跑全流程的情况下反复调提示词。
- **agent 把原本正确的关系改坏或删掉** → 所有修改在代码层强制要求原文依据；被删关系完整保留并在前端可见；默认关闭，过了评估门槛才开；`pre_agent_relations` 始终保留，可随时对比。
- **补充关系引入噪声** → 单任务最多补 5 条，证据必须能逐字定位；评估里单独统计新增类的正确率，不达标就在提示词里收紧或关掉"检查小节漏抽"这类任务。
- **耗时明显增加** → 串行加预算封顶，最坏情况是 80 次调用或 10 分钟；前端显示实时进展，等待过程不是黑盒。
- **百炼限流** → 默认串行；429 退避重试；预算耗尽时保留已完成的部分。
- **LangGraph 与 paddle 依赖冲突** → 第一项任务就验证；退路见决策 10。
- **框架版本升级改动接口** → 在 requirements 里锁定次版本；与框架的接触面限制在一个文件内。
- **任务状态 JSON 因事件增多而变大** → 状态里只留最近 20 条事件，完整轨迹只进结果。
- **规划质量不可控（漏掉重要疑点或任务清单过长）** → 任务数上限截断；规划失败有规则兜底；评估时对比"模型规划"和"规则直出"两种任务清单的效果。
- **实体合并出错会连带污染多条关系** → 规范名称必须在原文出现；合并记录进别名表，可在结果中查到每次合并，评估里单独统计。

## Migration Plan

1. 代码合入时 `AGENT_ENABLED=false`，线上行为不变。结果里新增的字段在关闭状态下只有 `agent_result.status = 未开启`。
2. 用重放脚本在已保存的结果上调试和评估，不影响线上。
3. 达到评估门槛后，在部署环境的 `.env` 里打开开关。
4. 回滚：把 `AGENT_ENABLED` 改回 `false` 并重启 worker，不需要回退代码或数据。已生成的结果里保留着 `pre_agent_relations`，可以直接取用。

## Open Questions

### 已验证的连接参数（2026-10-09，任务 1.3–1.4）

- 现有北京百炼部署接受并返回模型名 `qwen3.8-flash`；LangGraph 预制工具循环成功调用假工具，最终回答使用工具返回的随机值。这个实验确认接口模型 ID，不确认底层参数量。
- 不传 `enable_thinking` 时，非流式工具循环成功，两个响应的 reasoning token 数分别为 30、24，说明该部署默认启用思考。无需关闭也能连通，但为控制成本，核查适配器显式传 `extra_body={"enable_thinking": false}`；对照实验成功，未返回 reasoning token 用量。
- 两种模式都返回 `usage_metadata`（输入、输出、总令牌数）。默认模式两次调用总计 840 tokens、2.092 秒；关闭模式总计 711 tokens、3.443 秒。这只是单轮连通性实验，不能作为文档级成本或耗时评估。
- 可复现脚本：`scripts/probe-agent-connection.py`。基于独立 `AGENT_*` 配置或显式的 `--base-url`、`--model` 参数，不记录密钥或思考文本。
