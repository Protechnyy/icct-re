## Why

ICCT-RE 目前是一条固定流水线：每个 batch 只看得到自己那一节原文，证据定位和置信度都靠规则，LLM 没有任何主动行为。跨小节的指代（"该营"指谁）解不开，证据对不上时只能靠子串匹配兜底，系统里也看不到"智能体"。模型服务即将换到百炼（支持 tool calling、上下文足够长），现在是把 LLM 从"被动填表"变成"主动核查"的合适时机。

## What Changes

- 在并发抽取和规则去重之后，新增一个**文档级核查阶段**：由 agent 在整篇文档范围内核查抽取结果，再产出最终关系列表。并发抽取本身不改。
- agent 采用"规划、执行、记忆"结构：先由模型根据关系图概览和规则标出的疑点列出任务清单；再对每个任务跑有步数上限的工具循环；全程共享一份文档内记忆（实体别名表、已确认结论）。
- 提供一组只作用于当前文档的工具：检索原文、读取小节、定位证据、查询实体，以及修改关系图的动作（更正证据、合并实体、删除关系、补充关系）。
- 每一步工具调用和裁决都记入轨迹，随任务结果落盘；处理过程中把进展写入任务状态，前端可以看到任务清单、当前进度和每条关系的核查过程。
- 用 LangGraph 实现编排，模型走百炼的 OpenAI 兼容接口。
- 新增开关，可整段关闭 agent 阶段，行为回到现状；agent 阶段任何失败都回退到规则合并的结果，不让任务失败。
- agent 阶段单独限并发，默认值保守，避免触发百炼限流。
- 新增离线评估：用已保存的任务结果重放 agent 阶段，对比开启前后的关系质量和成本。

不在本次范围内：

- 跨文档的长期记忆。
- 面向用户的问答 agent。
- 抽取阶段内部（单个 batch 内）的工具调用。
- 把 PaddleOCR 拆成独立服务。仅当 LangGraph 与后端现有依赖装不到一起时才做，作为备选任务列出。

## Capabilities

### New Capabilities

- `document-agent-verification`: 文档级核查阶段的行为——何时运行、规划与执行的流程、文档内记忆、步数与并发上限、开关与失败回退。
- `agent-document-tools`: agent 可用的工具集——每个工具的输入、输出、作用范围，以及修改关系图的动作必须满足的约束。
- `agent-trace-and-progress`: 核查轨迹的记录与落盘、处理过程中的进展上报、结果接口与前端的展示。
- `agent-evaluation`: 离线重放与评估——如何在不重跑 OCR 和抽取的前提下对比 agent 开启前后的结果。

### Modified Capabilities

无。`openspec/specs/` 目前为空，没有既有规格需要修改。

## Impact

- **后端代码**：`backend/app/pipeline.py` 在抽取与合并之间插入新阶段；新增 `backend/app/agent/` 包；`backend/app/config.py` 增加 agent 相关配置；`backend/app/task_store.py` 的任务状态增加进展字段；`backend/app/api.py` 的结果和状态接口带出轨迹与进展。
- **前端代码**：`frontend/src/components/ResultViewer.jsx` 增加核查过程展示；任务列表显示新的阶段名和进度。
- **依赖**：后端新增 LangGraph 及其 OpenAI 适配器。与 `paddleocr==3.7.0`、`paddlepaddle==3.3.1` 的兼容性尚未验证，是实施的第一项任务。
- **模型服务**：需要百炼的 API key 和确切的模型名（27B 的 Qwen，型号待从控制台确认）。现有的 vLLM 抽取链路不受影响。
- **耗时与成本**：开启 agent 后，单篇文档的模型调用量预计为现在的两到三倍，实际数字由评估给出。
- **结果格式**：任务结果新增字段（轨迹、核查摘要、每条关系的核查状态），原有字段不变，对现有调用方兼容。
