# Design

## Context

上传接口使用 `file_type` 表达文件类型。PDF 和图片经过 PaddleOCR 版面解析及文档重构后构建文本块、章节并抽取关系。后续关系抽取、Skills 路由和结果保存接收普通文本，文本输入在解析阶段进入公共流程。现有结果含 OCR 专属字段和页码型 chunk 元数据。

## Goals / Non-Goals

**Goals:**

- 对 Markdown/TXT 直接读取 UTF-8 内容，并复用已有抽取和保存流程。
- 在任务状态和结果预览中准确表达文本来源，维持既有 PDF/图片行为。
- 保持历史任务 payload 和结果消费方可兼容。

**Non-Goals:**

- 从 Markdown 图片链接或 HTML 图片标签读取本地/远程图片。
- 引入新的编码探测库、文本解析依赖或富文本渲染器。
- 改变关系抽取或 Skills 路由算法。

## Decisions

1. **在文件类型识别处显式区分文本输入。** 增加文本类型常量及 `.md`、`.markdown`、`.txt` 后缀识别，后缀按小写比较；上传接口仍将类型写入现有任务 payload。扩展名是文本解码依据，不通过内容嗅探把任意未知格式当作文本。这样 Worker 能确定是否调用 OCR，且原有 PDF/图片分类保持不变；替代方案是在 Worker 内重新检查扩展名，但会重复上传校验逻辑并让任务类型不明确。

2. **以 UTF-8-sig 解码文本文件，并在进入模型步骤前拒绝空白或解码失败的输入。** 这会兼容普通 UTF-8 与 UTF-8 BOM；解码异常转成包含文件名的任务错误。无需额外编码依赖，也不会静默替换损坏字节。其他编码自动探测不在本次范围内，避免把乱码当成有效输入。

3. **仅在解析阶段分支，复用公共抽取主干。** PDF/图片继续执行 OCR、页面提取和文档重构。文本类型直接读取 `document_text`，跳过 OCR 状态、版面解析与重构，进入现有章节切分、chunk、关系抽取和保存流程。文本作为一个逻辑来源单元交给现有页码型 chunk/批次接口，页码字段使用 1；元数据同时标记 `source_type: "text"`，该页码代表逻辑单元。沿用现有页码型接口可以保持结果消费方兼容。

4. **保留结果对象形状，并让 `document_text` 成为原文预览的首选字段。** 文本结果仍含既有 OCR 相关键，但 `ocr_raw`、`ocr_pages` 与 OCR 重构内容为空，不伪造 OCR 输出；`document_text` 保存 BOM 移除后的 Markdown/TXT 原文。结果预览读取 `document_text`，并使用通用的“文档原文预览”文案；旧结果继续使用已有字段作为回退。OCR 专属耗时仅在实际执行 OCR 时写入。这样同一个结果视图兼容新旧任务，又不会把直接读取误标为 OCR。

5. **文本文件中的图片语法按普通原文处理。** Markdown 的图片引用保留在 `document_text` 供预览使用，不解析路径、不获取资源，也不送往 OCR。章节切分和抽取沿用现有 Markdown 文本处理逻辑。

## Risks / Trade-offs

- [单个逻辑来源单元上的关系仍会带页码 1] → 结果元数据增加来源类型，界面不将其解释为 PDF 物理页码。
- [大型纯文本文件可能占用较多内存并形成较大输入] → 继续使用现有 chunk 与批次限制；上传体积策略沿用当前配置。
- [非 UTF-8 文本会失败] → 错误中指出文件无法按 UTF-8 读取；本次不做有损解码或猜测编码。

## Migration Plan

无需数据迁移。已有队列任务仍使用原 PDF/图片类型值并沿原处理路径；部署新 Worker 后，新文本类型任务进入直接读取分支。回滚代码即可恢复此前的上传格式限制。
