# Design

## Context

动机和用户确认的展示范围见 `proposal.md`。界面及事件行为见本变更的两份规格。

- `Trace.emit` 分配递增 `seq`，保存字符串形式的 `result`，最多 500 个字符；进度回调包含完整任务清单及最近 20 条事件。
- `runtime.py` 的规划事件在模型返回后产生，工具事件在工具执行后产生。LangGraph 更新消息中的 `AIMessage.tool_calls` 和 `ToolMessage.tool_call_id` 已能提供调用关联信息。
- `Budget.invoke` 管理实际模型请求、调用次数、令牌用量和 429 重试，是记录每次模型请求的位置。
- `pipeline.py` 将进度回调写入任务状态，核查之后还有结果合并阶段。阶段状态和最终结果采用情况由这里与 `runtime.py` 共同提供。
- `RedisTaskStore` 保存任务 JSON 和结果 JSON，当前没有设置过期时间。API 直接返回任务状态和结果。
- `App.jsx` 每隔 2.5 秒读取未结束任务的状态；`ResultViewer.jsx` 在处理期间显示 `AgentProgress`，完成后显示摘要及逐关系详情。
- 工具返回已经具有结构：检索包含 `matches`，定位包含 `matched` 和 `locations`，小节读取包含 `text`、小节编号及页码范围，修改工具包含 `change.before`、`change.after`、`evidence`、`pages` 等。
- 现有核查功能来自正在进行的 `add-document-agent-verification`。本变更新增的两个能力与其最近事件及逐关系详情要求共同适用。

## Goals / Non-Goals

**Goals:**

- 事件与实际执行一一对应，调用开始、结束、错误和最终采用情况可追溯。
- 保留现有接口字段，新增数据按版本识别，完整事件在运行期间可查询。
- 任务详情主区域能够连续展示运行过程，并支持用户阅读历史步骤。
- 展示所需的信息从实际任务、工具返回和最终结论取得。

**Non-Goals:**

本次实施范围限定为执行记录、数据查询与过程展示；抽取规则、模型选择、模型思考配置、工具业务动作、资源预算及核查结果采用规则沿用当前实现。

## Decisions

### 1. 事件保留现有字段并增加版本和详情

新事件使用 `version: 2`，保留 `seq`、`task_id`、`kind`、`tool`、`args`、`result`、`truncated`、`elapsed_seconds` 和 `relation_ids`。增加 `document_task_id`、`timestamp`、`phase`、`status`、`call_id`、`summary`、`result_data` 和 `detail_available`。

`task_id` 继续指核查任务，`document_task_id` 指上传后的文档任务。离线重放入口提供自己的文档编号。时间使用 UTC ISO 8601，耗时使用单调时钟。

`result_data` 保存工具实际返回的对象或模型最终结论。`summary` 从真实返回数据提取命中数量、修改类型和错误说明，长度最多 500 个字符。保留 `result` 的现有字符串摘要供既有组件读取。JSON 读写使用标准库或浏览器已有的 JSON API。

工具自身的原文截断标识保留在详情中。详情保存工具实际提供的内容，工具内部的长度限制继续有效。模型请求事件只保存调用状态、任务关联及用量等元数据。

### 2. 在实际调用位置记录生命周期

`pipeline.py` 创建本次核查共享的 `Trace`，绑定文档编号、事件保存回调及现有进度回调，并通过新增的可选关键字参数传入 `verify_document` 和 `run_verification`。阶段边界、规划、任务执行和模型请求使用同一个记录器。独立重放入口也创建共享记录器，直接提供文档编号并记录阶段边界。既有位置参数调用方式继续有效。

| 活动 | 开始事件 | 结束事件 | 记录位置 |
| --- | --- | --- | --- |
| 核查阶段 | `phase_start` | `phase_end` | `pipeline.py` 的核查调用边界 |
| 任务规划 | `plan_start` | `plan` | `runtime.py` 的规划节点 |
| 核查任务 | `task_start` | `task_end` | `runtime.py` 的执行节点 |
| 模型请求 | `model_start` | `model_end` | `Budget.invoke` 中每次实际请求 |
| 工具调用 | `tool_start` | `tool` | 框架工具调用上下文与实际工具函数边界 |
| 核查结论 | — | `conclusion` | 执行节点确认任务结论时 |

每次实际模型请求有独立 `call_id`，包括预算内已经存在的重试请求。工具使用框架提供的调用编号，将开始事件、实际函数返回和 `ToolMessage` 对应起来。参数检查未通过的调用也具有成对事件，重复错误消息按调用编号归并。

模型调用的结束状态表达请求完成或请求错误。工具状态区分完成、业务动作拒绝和执行错误；空检索结果是正常完成。只有实际发生的调用能够产生调用事件。

`Trace` 将分配序号、保存事件和发布快照置于同一个同步范围，保证工具节点同时返回多条消息时序号唯一且保存顺序一致。事件保存回调的错误在调用位置直接传播。

`phase_end` 在取得实际核查结果后记录，包含状态、结束原因、任务状态数量和改动采用信息。`RelationWorkspace.record` 为过程改动增加稳定的 `change_id`；阶段结束记录给出 `accepted_change_ids` 与 `discarded_change_ids`。结果中的 `changes`、`discarded_changes` 与这些编号一致。阶段结束事件加入返回结果中的 `agent_result.trace` 后再保存最终结果。页面在结束前将过程改动标记为“已执行，最终采用情况待确认”。

### 3. 运行期间使用 Redis 保存完整事件

在 `RedisTaskStore` 中增加事件保存和查询方法，每个文档任务使用：

- `docre:agent:<task_id>:events`：Redis List，按 `seq` 顺序保存事件摘要和元数据。
- `docre:agent:<task_id>:details`：Redis Hash，以 `seq` 为字段保存完整事件 JSON。
- `docre:agent:<task_id>:meta`：Redis Hash，保存版本、最新序号、阶段状态和最终采用信息。

通过 Redis transaction 一起追加摘要、写入详情和更新最新序号，完成后更新任务状态中的 `agent_progress`。执行中不裁剪事件；保存期限与现有任务、结果一致。

`agent_progress` 继续提供任务清单、当前任务和最近 20 条事件，增加 `version`、`phase`、`status`、`last_seq` 与当前活动描述。列表页继续通过状态快照显示简短进度。

`agent_result.trace` 保存同一版本的完整事件，随现有 `result.json` 保存。结束后既可以通过事件接口读取，也可以通过已有结果字段导出。阶段关闭或跳过仍然有明确状态。

### 4. 事件列表分页，详情按需读取

`GET /api/agent/<task_id>/events?after_seq=0&limit=100` 返回：

- `version`、`events`、`next_seq`、`last_seq`、`has_more`；
- `phase`、`status`、`tasks`、`current_task`、`summary`；
- 已结束阶段的改动采用信息。

`after_seq` 是非负整数；`limit` 默认 100，允许 1 到 200。事件数组只包含摘要、参数及元数据，不携带 `result_data`。读取一轮先确定最新序号，再读取截至该序号的页面，新的事件留给下一轮；空页面保留原游标。

`GET /api/agent/<task_id>/events/<seq>` 返回完整事件，`seq` 为正整数。不存在的文档任务或事件返回 404，非法参数返回 400；存储读取错误在当前请求返回错误。

历史已保存结果通过版本分支读取已有 `agent_result.tasks` 和 `trace`，提供实际存在的摘要、参数和结论。没有结构化详情的事件标记 `detail_available: false`；详情请求返回已有事件及该标识。运行中的新版本记录即使暂时没有事件，也可从任务状态取得阶段信息。

### 5. 主区域使用一个持续存在的过程组件

在 `ResultViewer.jsx` 的任务标题与结果标签页之间放置统一的过程组件。该组件以事件查询数据及 `agent_result` 为输入，处理中的任务和已结束任务使用同一结构。

顶部显示“智能体校验过程”、核查阶段状态、当前活动、已完成数量及总数。规划尚未返回时总数显示“待确定”。主体左侧显示有序任务列表，右侧显示所选任务的执行时间线。

四类信息的阅读顺序：

1. **规划任务**：任务类型、目标、模型提供的理由及任务来源。规划仍在进行时显示等待状态。
2. **执行步骤**：模型请求与工具调用按事件顺序排列；同一 `call_id` 的开始、结束事件合并为一项。默认显示工具名称、参数摘要、状态和耗时。
3. **查看依据**：展开工具步骤时读取详情；按 `matches`、`locations`、`text` 等真实字段显示原文、小节和页码。相近句子使用“候选原文”标识，精确命中使用“已定位证据”标识。
4. **形成结论**：显示任务结论，以及 `change` 中的改动前后内容、证据、理由和位置。结束状态明确标识已采用或未采用。

调用结束后展开详情采用已有 Arco Design 组件；参数以标签和值显示，未知工具显示英文原名及现有数据。现有逐关系详情抽屉继续提供关系与任务的关联查看。

继承当前界面颜色、字体和间距，任务列表约占主体宽度的三分之一。过程区域具有独立滚动空间，运行期间优先提供足够阅读高度，完成后允许折叠主体并保留标题、状态和统计。结果标签页继续可访问。

任务列表项和展开操作使用可聚焦控件；状态同时提供文字和颜色。等待时长只由开始时间计算，结束时使用后端耗时。DOM 尺寸检查覆盖当前项目支持的桌面视口。

### 6. 增量数据按文档任务管理

`App.jsx` 为各文档任务保存事件、游标、详情缓存和读取状态。当前选中任务在核查开始后每隔 2.5 秒查询增量事件；`has_more` 为真时立即读取下一页。记录按 `seq` 去重，只有已成功接收的事件才能推进游标。

切换任务时取消旧请求，异步返回前核对文档任务编号；缓存始终按文档任务分别保存。刷新页面从 `after_seq=0` 分页恢复，状态和事件读取失败分别显示对应错误及重新读取操作。

任务处理状态结束后仍需完成最后一次事件同步，确认已读取 `phase_end` 且游标达到后端最新序号。最终结果补充任务状态和改动采用情况。已经有新版本事件时，旧快照中的最近事件仅用于简短进度。

默认跟随当前任务。用户主动选择历史任务或滚动阅读早期步骤后暂停自动切换，显示“跟随当前任务”操作。展开状态以文档任务编号及调用编号保存，更新事件保留选择、滚动位置和键盘焦点。

### 7. 验证使用实际服务与记录

- 事件数据检查使用项目已保存结果中的原文、关系和真实工具调用结果，直接调用工具及事件序列化逻辑，验证参数、位置、摘要与详情的对应关系。
- 存储和 HTTP 检查使用真实 Redis 及实际 Flask 应用，在独立测试文档任务编号下验证顺序、分页、空页面、非法参数、不存在任务、详情和重复读取。
- 真实模型重放使用已保存的项目文档结果，核对实际调用日志、事件和最终结果；另外设置较小的真实调用预算验证部分完成和未采用改动的状态表达。
- 浏览器使用真实 API 和上述运行记录，通过 DOM、键盘操作及滚动检查验证任务选择、展开证据、刷新恢复、切换任务和结束后的完整读取。
- 中间验证材料写入项目内专用且已被 `.gitignore` 忽略的目录，例如 `.impeccable/checks/agent-workspace/`，记录调用编号、事件序号、断言结果及构建结果。

## Risks / Trade-offs

- 轮询期间工具可能快速完成 → 记录开始与结束事件，分页补充所有新增事件；页面按完整顺序展示，更新延迟由现有 2.5 秒轮询决定。
- 多个工具返回造成编号和保存顺序竞争 → 序号分配与事件保存使用同一个同步范围，Redis transaction 保证摘要与详情共同可读。
- 大量关系改动使详情增大 → 列表接口只发送摘要，详情按需读取；模型和任务数量继续受已有预算限制。
- 任务成功后最后事件尚未读取 → 客户端完成最终事件同步后才停止读取。
- 过程修改可能最终未被采用 → 用稳定改动编号与阶段结束记录展示最终采用情况。
- 历史结果缺少时间和结构化原文 → 展示已有内容并标记信息缺失。
- 事件保存服务发生错误 → 在读写位置直接报告错误，保留已经读取的页面内容及现有任务错误状态。

## Migration Plan

1. 部署后端事件记录、保存和新增接口，新生成结果使用 `version: 2`；核查开关及现有结果字段继续使用当前配置。
2. 部署前端主区域组件和查询逻辑，按记录版本读取运行任务及历史结果。
3. 使用真实 Redis、模型重放和浏览器完成规格场景检查，核对四类信息与实际执行记录对应。
4. 需要恢复文件内容时，通过文件编辑工具恢复本变更修改的文件；已生成记录保留版本标识供后续读取。
