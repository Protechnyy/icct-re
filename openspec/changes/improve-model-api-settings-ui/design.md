# Design

## Context

动机见 `proposal.md`。当前 `App.jsx` 使用 `view === "settings"` 替换主页面，`ModelSettings.jsx` 负责读取配置、编辑两个字段及提交保存。顶部入口已位于服务状态旁，现有 `SkillManager.jsx` 使用 Arco Modal、自定义底部按钮和关闭后的焦点恢复，可以沿用这些交互方式。

配置读取接口返回 `base_url`、默认模型 `model`、`backend` 和 `api_key_configured`，不会返回已保存 Key。更新接口目前只接受地址和可选的新 Key。配置文件保存地址及 Key；`VllmClient` 的健康检查和实际请求分别读取配置中的模型值。本次增加可保存的模型名称，并让读取结果同时提供默认模型和当前生效模型。当前 `refreshHealth` 独立处理健康检查失败。前端已有 Modal 样式导入，尚无独立的前端测试脚本。

本次需要父页面、弹窗状态及异步请求共同管理编辑内容和关闭流程，因此保留设计文档明确这些决策。

## Goals / Non-Goals

**Goals:**

- 让弹窗的可见状态独立于任务中心、Skills 的页面状态，保持原组件和用户输入。
- 将配置读取状态、地址和模型草稿、Key 编辑状态及请求错误分别管理，保证关闭及重新打开时状态明确。
- 支持默认模型和自定义模型名称，并让主模型请求及健康检查使用同一个生效名称。
- 将保存结果与服务健康状态分别表达，并兼容已有配置文件和只提交地址、Key 的客户端。

**Non-Goals:**

- 独立的模型设置页面或导航路由。
- 多配置列表、切换后端类型或模型目录选择、Key 删除、专用连接测试接口。
- 环境变量及 OCR 部署流程的修改。

## Decisions

### 1. 顶部入口打开居中弹窗

顶部入口复用 `Skills` 当前使用的 Arco `Button` 和 `IconRobot`，采用 `type="text"`，左侧机器人图标、右侧 `Qwen / vLLM` 文字。字号、文字颜色、图标间距、按钮内边距和悬停、键盘焦点效果与 `Skills` 的文字按钮一致。服务状态右侧的分隔线由入口外层容器保留，按钮使用自身的完整点击区域；窄屏时也保留入口。

按钮声明 `aria-haspopup="dialog"`，并根据弹窗状态更新 `aria-expanded`。页面选中状态由任务中心和 Skills 的导航按钮表达；模型入口使用对话框的打开状态。这样入口在外观上与已有导航按钮一致，并能向键盘及辅助技术用户表达它的实际操作。

`App.jsx` 增加独立的 `modelSettingsVisible` 状态，顶部按钮只打开弹窗，主区域继续按照原 `view` 渲染任务中心或 Skills。移除独立设置页的分支，将懒加载的 `ModelSettings` 放在主内容之外，通过 `visible`、`onClose` 和 `onSaved` 协调操作。首次使用时加载组件，后续打开仍重新读取配置。

选择 Arco Modal，宽度以 520px 为设计默认值，并限制为窗口宽度减去两侧各 16px；内部采用单列字段，内容超高时滚动。弹窗标题为“模型设置”，表单依次提供 API Key、API 请求地址和模型名称，底部放置“取消”和“保存”。模型名称字段显示当前生效名称，并说明默认模型；Key 状态及后端信息作为辅助说明。字体、间距、颜色沿用 `index.css` 中的变量，替换现有页面卡片样式。

独立页面会中断当前工作台显示；侧边抽屉占用较多宽度。三个单列字段适合放入弹窗，并复用已有组件。

### 2. 用明确操作进入 Key 编辑

配置读取成功后，已有 Key 时默认展示“已配置”和“更换 Key”；点击更换后显示 `Input.Password`，辅助文字说明留空保留当前 Key。提供“取消更换”操作，只清空 Key 草稿并结束 Key 编辑，保留地址草稿。未配置 Key 时直接显示密码输入框，并说明兼容无 Key 的模型服务。

密码可见切换仅作用于新输入内容。表单不展示已保存 Key 的字符、末尾片段或模拟遮挡内容，不在浏览器持久存储或日志中记录 Key。

长期显示空密码框容易使用户无法判断是否已配置。使用状态加编辑操作可以直接表达当前配置和用户即将进行的更换。

### 3. 保存自定义模型名称并兼容默认配置

`config.skill4re_model` 作为远程主模型的默认名称。配置读取接口返回 `model`（当前生效名称）和 `default_model`（配置默认名称）；没有自定义名称时，两者相同。前端打开弹窗后将 `model` 填入可编辑字段，并显示 `default_model` 作为说明。用户修改名称后保存自定义值；清空字段后保存表示恢复默认名称。

`ModelSettingsStore` 为模型配置增加可选名称。现有 `model.json` 未包含该字段时按默认名称读取，不要求迁移文件。更新请求带有 `model` 时，空白或等于默认名称表示清除自定义值，其余非空字符串保存为自定义名称；省略 `model` 时保留当前名称，以兼容只更新地址或 Key 的旧客户端。API 返回生效名称和默认名称，不返回 Key。

`VllmClient` 的健康检查和快速抽取请求，以及 `Skill4ReClient` 的远程抽取请求，均使用同一个生效模型名称，避免界面显示与请求内容不同。自定义名称仅影响当前远程主模型配置；本地后端仍使用原有配置。

选择可选字段让已有配置文件继续工作，也允许配置默认名称更新后自动生效。将清空定义为恢复默认，能直接从弹窗返回配置中的默认名称。

### 4. 每次打开读取，关闭清除草稿

区分 `settings`、`baseUrl`、`model`、`apiKey`、`editingKey`、`loading`、`saving`、`loadError`、`saveError` 和字段错误。每次打开重新读取配置，先清除上次 Key 输入和错误，读取完成前禁用保存。读取失败保留弹窗及重试操作，服务端 409 等错误直接展示实际说明。

对配置读取增加请求代次或取消标记；已关闭弹窗或旧读取请求的结果不能覆盖新一次打开的内容。清除草稿发生在实际关闭或保存成功时。使用 `afterClose` 恢复顶部入口的焦点；不能只依赖表单内容卸载，因为组件自己的 React 状态可能仍然保留。

保留上一次草稿会使新打开的弹窗与当前后端配置不一致，尤其是新 Key 内容。因此选择重新读取，并在关闭确认中处理未保存修改。

### 5. 校验及显式提交

前端使用浏览器 `URL` 对象和空值检查校验地址，要求 HTTP 或 HTTPS；字段错误关联输入并将焦点移到地址。模型名称去除两端空白后保存；空值表示恢复默认。服务端继续完成用户名、密码、查询参数及片段等已有完整校验。表单提交包含 `base_url` 和 `model`，只有非空的新 Key 才添加 `api_key`。沿用 `getModelSettings` 和 `updateModelSettings`。

保存按钮位于 Modal 底部，通过 `form` 属性提交正文表单，键盘提交使用同一处理方法。请求进行中使用提交保护及 `saving` 状态阻止重复请求、编辑、取消和关闭。保存失败将实际错误显示在弹窗内，保留全部输入并恢复操作；错误区域使用可访问的提示或焦点，使用户能发现失败原因。

不对字段变化自动保存，用户可以在确认提交前完成地址和 Key 的组合编辑。

### 6. 保存结果独立于健康检查

更新接口成功返回后，立即清空新 Key、显示“模型设置已保存”，通过父组件关闭弹窗并调用现有 `refreshHealth`。更新请求错误的处理范围仅覆盖保存请求；刷新健康状态不会使已经成功的保存显示为失败。

“已配置”只说明 Key 存在。顶部服务状态继续表达实际依赖检查结果，用户能够区分保存成功与服务可用。

### 7. 统一关闭流程和键盘行为

取消按钮、关闭按钮和 Escape 使用同一个关闭处理方法。保存期间暂停关闭。其他状态下，若地址或模型名称草稿与已读取值不同，或新 Key 非空，则展示放弃修改确认：“继续编辑”保留弹窗和草稿，“放弃修改”清除草稿并关闭。仅打开 Key 编辑而没有输入不视为修改。

`maskClosable` 设为 false，保存期间暂停 Escape 并隐藏或禁用关闭按钮。使用现有 Modal 的焦点管理能力，在打开后让地址输入获得焦点，关闭后恢复到顶部按钮；放弃修改确认也保持对话框内的键盘访问。

点击遮罩直接关闭会绕过明确操作，尤其容易丢失刚输入的 Key，因此使用明确的关闭入口。

## Risks / Trade-offs

- [旧读取结果覆盖新一次打开的配置] → 使用请求代次或取消标记，并在实际关闭时清除草稿。
- [保存进行中关闭导致无法解释结果] → 暂停关闭和重复提交，结束后按真实响应恢复操作。
- [网络错误发生时服务端可能已经保存] → 显示请求失败并保留草稿；重新打开时读取服务端当前配置。
- [旧配置没有模型字段] → 读取时使用默认模型，首次保存时按用户输入保存或清除自定义名称。
- [窄屏或长错误信息遮挡操作] → 限制弹窗宽度和正文高度，错误文字换行，验证 320px、768px 和桌面窗口中的 DOM 尺寸及滚动可达性。
- [真实保存验证改变日常配置] → 在隔离的本地验证服务及独立存储目录中检查保存和 Key 保留，使用实际接口，避免修改日常使用的配置文件。

## Migration Plan

1. 扩展后端配置读取、保存和主模型请求，再更新前端入口、弹窗表单及样式。
2. 完成后端配置与 API 检查、前端构建和本地服务验证后，通过当前功能分支提交相关修改，按项目流程审查。
3. 部署前端和后端即可使用新界面；已有配置文件会继续使用默认模型。若恢复原界面，保留已保存配置及自定义模型名称。
